# 经验教训

从各阶段的工作日志、任务单和进度记录里整理出来的实际踩过的坑（原文在 git 历史里）。每条写现象、根因和以后怎么避免。
`.claude/skills/mcpe-porting/PITFALLS.md` 是给 AI 的速查清单，这里是带来龙去脉的版本，两者有重叠。

## 一、浮点与 C++ 数值语义

1. **`f()` 包不包看的是 C++ 原句有没有 `f` 后缀。** 曾把没有后缀的 `-0.7` 也包成 `f(-0.7)`——那是 double 字面量，比较按 double 提升做，包了反而错。判据不是“这个数精不精确”。
2. **被黄金样本钉住的渲染代码不享受“第三档自由处理”。** 模型 UV 里的 `-0.002f / texW` 不是 float32 能精确表示的数，少包一层 `f()`，夹具里的 `0.375031263` 就变了。
3. **不要凭推断去改已经通过黄金样本的代码。** 曾以为 `getTimeOfDay` 的 `cos` 应该走 float 重载，改完 S4 样本立刻对不上——原来的 double 写法本来就与 C++ 逐位一致。标记写着“有差异”时，先拿样本验证再动手。
4. **头文件里不带 `Mth::` 的 C 库函数走 double 版本**（`sin`、`cos`、`sqrt`、`pow`），而 `Mth::floor` 只有 float 版本（double 实参先被转成 float）。不带 `Mth::` 的 `abs(float)` 是 float 版本——这一点只有专门导出的 treeShape 表能分辨。
5. **`int seed = random->nextLong()` 会截断成 32 位**，再拿去 `setSeed`。照抄类型转换，别把 64 位值直接传下去。
6. **`t.color(255, 255, 255, 255)` 在 C++ 里选中的是 int 版重载**，而 TS 的四参 `color` 是 float 版（内部乘 255）。照字面抄算出 255×255 再被钳回 255，看着也对，纯属侥幸。必须写 `colorInt`。
7. **期望值不要在测试里重算，直接用被测的常量。** 曾把 `Mth.RADDEG` 重算成 `f(180 / Math.PI)`，而它是 `f(180 / f(PI))`，差最后一位；还把方向说反了（它是弧度转度）。
8. **`f(0.5)` 与 `0.5` 逐位相等**，把 `f(0.5)` 改成 `0.5` 的变异必然抓不住，不是测试有问题。设计变异时要挑真能改变结果的。
9. **`NaN` 之间用 `toBe`（`Object.is`）是相等的。** 把 `Math.random` 定死成 0.5 时，抖动恰好为 0，速度除以 0 得 NaN，一条“漏掉 ×0.1f”的变异因此骗过了断言。测试里固定随机数时要检查会不会造出退化输入。
10. **未初始化内存只有“连跑两次比对产物”才抓得到。** 黄金样本里有两处字段每次运行都不同，靠一次带 `MALLOC_PERTURB_` 的运行比出来，标成 `uninit`。

## 二、继承与对象模型

11. **C++ 的非虚函数在 TS 里写成同名方法就变成了“虚”的。** `Entity::reset` 调的是 `Entity::_init`，TS 里却派发到了 `Player._init`，`Entity._init`（清掉“已移除”等标志）从不执行——玩家死后被移除，点“重生”后血量恢复了却仍是死的。父类调用非虚函数时写 `Entity.prototype._init.call(this)`。
12. **构造期间的虚函数调用要写成 `本类.prototype.方法.call(this)`，但只限基类构造。** 粒子子类在自己的构造函数里调 `tick` 是正常的虚调用，曾有人建议也写成 `Particle.prototype.tick.call(this)`，那会接上基类的 tick（少了 `yd -= 0.02f`），反而是 bug。
13. **C++ 按值传参，TS 别存引用。** `Player::startUsingItem(ItemInstance instance, …)` 是按值的；TS 存了引用，吃完东西 `setNull()` 把背包里那一格也清成了 id 0，下次右键崩溃。修法：`this.useItem = new ItemInstance(instance)`。
14. **方法名可能遮蔽同名字段**（`Spider::makeStepSound` 遮蔽了基类的同名字段），TS 里同名就会冲突，按 R10 改名。
15. **估工作量之前先读继承链。** 曾估“鸡只需要 Mob 的骨架”，读源码才发现是 `Chicken → Animal → AgableMob → PathfinderMob → Mob`，中间少两级，计划只好拆开重排。`TripodCamera` 继承的是 `Mob` 不是 `Entity`，但它的 `tick` 不调 super。
16. **原版的“明显错误”多半要保留。** `HangingEntity` 构造参数被丢弃、NBT 同时写 `Direction` 和 `Dir`、`Arrow` 与 `Throwable` 两份相似但有差异的代码……都照原样，并在文件头列出差异。

## 三、模块加载与运行时

17. **基类 import 子类会触发 “Class extends value undefined”。** 用注入（`XInclude.ts`、钩子模块）。注入用的钩子模块（`MobSpawnerHooks`）必须从包入口导出，否则注册代码根本不执行，刷怪静悄悄地不工作。
18. **跨类读静态字段会拖进加载循环时，可以经实例取**：`RandomLevelSource.postProcess` 读 `HeavyTile.instaFall` 时用 `Tile.sand.constructor`，避免 `HeavyTile → FallingTile → Entity` 的加载链。
19. **没有任何 import / export 的 `.ts` 是“脚本”不是“模块”**，`tsc` 报 `TS2306: … is not a module`，加一句空的 `export {}`。
20. **`declare function f()` 能通过类型检查，但运行时不存在。** 一律用真的 import。

## 四、随机数与遍历顺序

21. **随机数要与 C++ 同构，包括“哪个随机源”。** `Mth.random` 背后是模块级的一个 `Random`，`random(n)` 是 `nextInt(n)`，不是 `floor(nextFloat() * n)`；粒子的初速度抖动用 `Mth::random()`、尺寸寿命用 `sharedRandom`，两个源不能合并。
22. **取随机数的顺序必须和 C++ 写的顺序一致。** 矿石生成里是先取 x、再取 y、再取 z、再放置；写成数组循环时要展开，保持这个顺序。C++ 里被注释掉的大树留下了空的 `if (random.nextInt(n) == 0) {}`，这些空分支照样消耗随机数，必须保留。
23. **列表的顺序可能和声明顺序不同。** 画的 `getAllMotivesAsList()` 里 `Aztec2` 排在 `Alban` 前，`Aztec` 根本不在列表里，随机画作的分布建立在这个顺序上。
24. **边遍历边删要 `splice(i, 1); i--`**（C++ 的 `list.erase(list.begin() + (i--))`），顺序错了会漏掉元素。
25. **`goto` 重启整个循环**要写成带标签的 `for (;;) { for (…) { … continue label; } break; }`，不能简化成 `continue`。

## 五、存档与浏览器平台

26. **IndexedDB 的 `tx.oncomplete` 必须在创建事务的同一个任务里挂上**，等 `await` 完再挂会永久挂死。
27. **`Uint8Array.set(Int32Array)` 会静默截断**（逐元素拷贝）。字节视图要按字节构造。
28. **共享内存的视图用 `subarray` 不用 `slice`**（C++ 的指针语义），而且打包文件里每段的 `byteOffset` 不是 0，读头要带上 `data.byteOffset`。
29. **测试助手忘设 `storageVersion` 踩了两次**：默认 0，而 `readLevelData` 只认 `== 1` 与 `>= 2`，版本 0 静默什么都不读，症状是“世界列表里名字是空的”。已写进测试助手的注释。
30. **选项存进 IndexedDB 后刷新不会恢复。** 把“菜单风格”改成当时还没移植的经典风格后，起始菜单为空，页面黑屏，刷新也一样。凡是会被选项改变行为的界面，都要测“所有选项设到最大 / 最小后重启”。
31. **区块一旦存下就不会追溯生成地物。** 地物移植之前生成的区块被标为 `terrainPopulated`，之后再加地物也不会补上，测试用的世界要删掉重建。
32. **`VirtualFS.remove` 删不掉非空目录**（照抄 C++ 的行为），删世界目录前要先删 `players/`。

## 六、渲染与素材

33. **网页版只从预加载表取贴图，漏了一张就“画错了图”，不报任何错。** 这个坑踩了至少六次：告示牌画成地形图集、玩家皮肤采到地形图集（头顶草地绿）、暗角画成 icons.png……新代码用到新贴图时同步加进 `apps/web/src/assets.ts`。
34. **测试里用 `Mth.sin` / `Mth.cos` 之前要 `Mth.initMth()`。** 65536 项的表在模块加载时全是 0，症状很怪：`-cos(0) * 5` 得 `-0`，常量算出一半。
35. **测试里建模型或渲染分派器之前要先铺 GL 上下文**（`glSetContext(new GLES1(null))`），模型构造要 `glGenBuffers`。一次注册改动曾连带打坏 21 条旧测试，修的是测试环境，不是断言。
36. **`Tesselator.draw()` 自己会发 4 条客户端数组开关**，记录 GL 调用的断言要把它们算进去。
37. **法线是 `v1.cross(v0)`，不是 `v0.cross(v1)`**，顺序反了整个模型的光照就反了。
38. **“逻辑全对但画面上看不见”通常是渲染器没注册或没移植。** 实体渲染分派器拿不到渲染器就静默跳过。注册那一行比渲染器本身更容易漏，测试要钉“注册表里真的有它”。

## 七、黄金样本与 harness

39. **harness 没调 `Mth::initMth()`，地物样本第一次就对不上。** 黏土用 C 库的 `sin`、矿石用查表的 `Mth::sin`，表没初始化时后者全是 0。
40. **`build.sh` 少了 `-DOPENGL_ES`**，`ModelPart::draw()` 走了显示列表分支，和网页版行为相反。
41. **陷阱桩规则误伤了小写 `rak` 开头的符号**（`rakMalloc_Ex` 等不含 “RakNet” 字样），程序没进 `main()` 就崩。用 `nm --undefined-only` 查清楚再补规则。
42. **生成夹具之后立刻解析一遍。** 曾改 JSON 输出时漏了一个闭括号，夹具多一个 `]`。
43. **样本要能分辨你关心的细节。** 大树的 6 棵树在 `abs` 用两种写法时都能通过；挑地形测试区块时“阈值满足”不等于“分支会走到”（砾石还套着水面高度的窗口）；早期地形样本的区块全在真实世界之外，世界内一个都没比过。
44. **`clean.py` 会删掉 `#include` 行**，看它的输出会误以为 `ModelInclude.h` 是空文件（其实有 9 条 include）。判断文件内容时用原文件。

## 八、测试与验证流程

45. **`vitest` 不做类型检查。** 测试全绿而 `pnpm typecheck` 报错的情况出现过多次，有一次就这样提交了。提交前先跑类型检查。
46. **变异工具本身可能是假阳性。** Windows 上 `execFileSync('npx')` 没带 `shell`，每条变异“立即红”，一次测试都没跑，30 条 0.3 秒“全过”。修好后补跑了全部 102 条。另一次是回退方式有问题（用字符串替换回退，碰到原串出现两次就改坏了文件），改成先备份、从备份还原。
47. **数标记用台账那条严格正则。** 宽松的 `grep` 会把正文里提到标记的说明文字也算进去，曾因此写错完成报告里的数字。
48. **浏览器场景里 `h.state` 的回调会被 `toString()` 后在页面里重新求值**，闭包全丢，引用 Node 侧的变量就是 `ReferenceError`。自己写了这条注意事项，然后自己又踩了一次。
49. **全部测试一次跑完超过 5 分钟**，需要分批；个别启动整个应用的测试在并行时会撞上默认的 hookTimeout，那不是新改动引入的，放宽超时即可。
50. **`prettier --write` 之前先对基线 `--check` 一次**：它会改整个文件的行尾符，造成全文件 diff，而基线本来就不通过。
51. **`pnpm ci` 是 pnpm 自带的子命令**（等于 `install --frozen-lockfile`），会盖过 package.json 里的同名脚本，什么都不检查。要写 `pnpm run ci`。
52. **`setIfNotSet(flag, f())` 不能写成 `flag || f()`**：`f()` 有副作用，C++ 总会先求值，`||` 会把它短路掉（熔炉放不进物品）。
53. **后置自增是坑**：`checkInterval++ == 100` 的检查发生在第 101 刻。
54. **测试的处境要和真实处境一致。** 平坦的 demo 世界永远是白天：测刷怪、睡觉要冻住天色；测僵尸追人要选夜里，不然僵尸先被太阳烧死。

## 九、判断失误的复盘

55. **“睡觉被不明原因叫醒”其实是正常的睡到天亮。** 把一天的长度记成了 24000（这一版是 19200），以为时间没跳；读日志又早了 0.7 秒，以为起床函数没被调用。之后加陷阱记录每次状态变化，才看到是 `awakenAllPlayers`。先确认常量，再加全程记录，再下结论。
56. **没核实就写进文档。** 曾写“台账 254 不变”，事后核对是 251；曾写“11 个实体看不见”，实测只有 5 个。数字和结论都要跑一遍再写。
57. **测试脚本自己写错会被误当成代码问题。** 例如把界面编号写错（选世界是 5 不是 1）、选项编号写错（渲染调试是 14 不是 19）、物品 id 忘了 +256。脚本里先打印对象的名字或类名，确认操作对象没错。
58. **截图里画面空白，先怀疑设定。** 掉落物摁在玩家眼睛高度，起点终点都在相机原点、卡在近裁剪面里；暂停后改的视角只被插值走了一小截，实体在视锥外。用隔离实验（换个摆放位置）把“设定问题”和“代码问题”分开。
59. **被代码名字骗过。** `SandTile` 看着是沙子，游戏里的沙子其实是 `HeavyTile`；这是浏览器场景里一条“不该排计划刻”的断言跑出 `+1` 才查出来的。拿不准时去注册表里查实际实例。
60. **性能要在目标环境里测。** vitest 会把 import 变成取值函数，热循环里的每次静态访问都多一层调用，Node 下的剖析把 `Region.getTile` 等放大到前几名；换到浏览器里测，同样的“优化”毫无效果。反过来，浏览器剖析一眼就看到了真正的瓶颈：进 demo 世界 48 秒里 92% 在 `CFile.write`。
61. **“逐次追加、每次整块重新分配”是平方级的。** `CFile.write` 每写 4 个字节就把整个文件拷一遍；单个写入看不出问题，几万次写入就是几十秒。这个问题藏了很久，只表现为“启动测试要 20 多秒”，当时被当成独立问题放宽了超时。超时变长时要先查原因，不要只放宽超时。
62. **对比画面前，先确认两边都“建完了”。** 远处一块浅色海面查了好几轮：补跑 2000 刻、先做完光照都没用，最后发现是 TS 还没建出来的渲染区块（透过去看到天空色）。强制重建只建“可见”的区块，而载入早期建成空的区块不会再参加视锥剔除，只能靠普通模式逐帧去建——原版几十帧/秒自然建完，无头浏览器 1 帧/秒差得远。用户一开始就猜“是加载时间的问题”，是对的。先做“全部重建后还在不在”这个最便宜的实验，能省掉很多推测。
