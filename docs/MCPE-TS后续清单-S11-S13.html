判定方法与边界

“能否完整移植”是对参考源码逐个单元做静态分析得出的，规则如下：

  • 单元直接 #include 的每个头文件都必须在该步结束时存在：要么已经移植（不是前向声明），要么是本步或更早步骤计划内的单元。计划内的单元即使是部分移植也算存在：部分移植按 R3 保留全部函数签名，只把函数体里依赖计划外系统的语句标 DEFERRED。
  • 通过 Entity*、Player*、Mob*、ItemEntity*、Inventory* 等指针访问成员（p->x），即使类型是经别的头文件间接拿到的，也算依赖该类；类型若在后面的步骤才移植，单元推迟到那一步。
  • 调用目前在 TS 里是 OMIT 的函数（例如 Level::addEntity、Level::getTileEntity、Tile::spawnResources）算作依赖“补完这些函数的那一步”。下面的阶段 A 会先把它们补成签名齐全的函数，所以不阻塞。
  • 某单元只要有一个依赖属于计划外系统（网络、粒子、声音、界面、合成、生物 AI、落沙与 TNT 实体、抛射物、树木生成……），就是部分移植，归 Claude。

边界与说明：

  • 这是静态分析，个别遗漏在所难免。移植中如果发现某个“完整移植”单元其实用到了还不存在的东西，不要自己造替身：照 R3 写 // DEFERRED(类别): 原句，并在交回时告诉我，我会把它挪到部分移植并修正清单。
  • 依赖玩家、实体的 21 个方块与物品类（门、楼梯、箱子、熔炉、作物、武器……）在 S11 就“几乎”能移植，为了不让一个文件经两个人的手，整份推迟到 S12、由你完整移植；它们在 initTiles、initItems 里的注册行留到 S12。
  • 新的顶层目录：src/nbt 放进 packages/world/src/nbt/，src/locale 放进 packages/world/src/locale/（决策 D11：world 要用，不能依赖 client）。

S11 里发现、以后移植时要注意的

  • 比较“S12 才注册的方块”的 id 要用 idOf()：tile === Tile.fenceGate.id 在 S12 之前会报错（访问了未注册的哨兵）；写成 tile === idOf(Tile.fenceGate)，未注册时得到 −1，注册后自动生效。S11 里 FenceTile、I18n、DyePowderItem 各有一处这样改了。只用于比较；写进世界或读纹理仍直接用 .id。
  • 构造函数里读其他方块的类，注册时间受那个方块限制：HatchetItem 的构造函数读 Tile.chest，所以 5 把斧子的注册留到 S12。
  • 包结构：nbt、locale 是独立的包（你的决定），依赖要写进 package.json；不要用 ../../nbt/src/... 这种跨包相对路径。locale 依赖 world、world 又依赖 locale，形成包之间的循环；目前只在函数内部互相使用，没有问题，但不要在模块顶层用到对方。
  • ES 模块循环：基类文件不要 import 子类（nbt 的 Tag 曾经这样，运行时报 “Class extends value undefined”）；需要“基类里 new 子类”时用注入（TileInclude、ItemInclude、TagInclude、TileEntityInclude）。
  • R10 改了：不再用 $n 后缀，见手册修订版 8 的 R10 对照表。
  • C++ 本身的未定义行为（CarriedTile 把未初始化的 tex 传给基类、多数方块的爆炸抗性赋值前就被比较）：黄金样本标为 uninit，不比较。

黄金样本

什么是黄金样本

黄金样本是用参考 C++ 源码本身算出来的标准答案，用来证明 TS 移植在给定输入下与原版结果一致。它由三部分组成：

  • harness：tools/golden/harness_*.cpp，一个很小的 C++ 程序，直接 #include 并链接参考源码里要核对的那些 .cpp（不改动参考源码；只为链接时用到、运行时不会调用的外部函数提供空的替身定义），用固定的输入调用被测函数，把结果写成 JSON 或二进制。
  • 夹具：fixtures/golden/*.json（或 .bin），即 harness 的输出，提交进仓库。重新生成的命令是 REF=<参考源码目录> ./tools/golden/build.sh；在 x86-64 Linux 上用 g++ 编译（与原版一致的 float 语义，long 为 64 位）。
  • 测试：tests/golden/*.golden.test.ts，用同样的输入调用 TS 实现，与夹具逐项比较。

比较方式随三档规则而定：

档位比较方式适用
第一档：必须一致逐位：整数完全相等；float 比较 32 位位模式；字节流逐字节相等；字符串完全相等种子 → 世界的链、方块与物品的 id 和注册数据、存档格式（NBT）、网络协议
第二档：结构一致，数值放宽容差：每个数值的绝对或相对误差不超过 1e-4；离散结果（落在哪个方块、是否碰撞、tick 次数）完全相等物理与碰撞、方块逻辑、AI
第三档：自由处理不做黄金样本，用单测与 dev 页截图渲染、GUI 布局、粒子、声音

现有的样本：random、mth、util、s4（群系、区块随机、亮度、昼夜）、synth（噪声）、biomesource，共 6 组，全部第一档。

夹具里带 uninit 标记的字段，是 C++ 读了未初始化内存的地方（build.sh 用 MALLOC_PERTURB_ 跑第二遍找出来）。最常见的是 explosionResistance：setDestroyTime 拿它和 destroyTime×5 比较之前从未赋值。夹具取零初始化时的值，TS 字段初值为 0，结果一致。

移植 NBT、ItemInstance、I18n 时要保留的 C++ 行为（黄金样本会检查）

  • CompoundTag 用 std::map 存子标签：写出顺序按名字排序，不是插入顺序。
  • ByteArrayTag::load 读了长度和数据，却没有设置 data.len：读回后再写出，长度为 0 且没有数据（nbt.json 里 root 338 字节、reread 333 字节，差的就是它）。
  • 字符串：writeString 写长度 length & 0x7fff（short）再写原始字节；readString 用 C 字符串构造 std::string，遇到 0 字节截断，长度上限 SHRT_MAX − 1。
  • putDouble 的参数是 float（先截成 float 再存成 double）；需要真正的 double 时 C++ 直接 put(new DoubleTag(…))。
  • 所有数值按小端写（BytesDataOutput 直接写内存）；long 是 64 位。
  • ItemInstance::save：id、Damage 用 (short)，Count 用 (unsigned char)（例如 200 写成 0xC8）；fromTag 在物品不存在（例如 id 0）时返回 NULL。
  • I18n::fillTranslations 用 insert，已有的键不会被覆盖（即使 overwrite 为 true）；键和值两端去空白（语言文件是 CRLF）；找不到时 get 返回 id + "<"。
  • getDescriptionString：羊毛、栅栏门、半砖有特例；其余先转小写，把 tile./item. 换成 desc.，查不到再删去材质词（wood、iron……）重查，最后返回 desc + " : couldn't find desc"（185 条里有 28 条是这样）。

harness 的编译方式

  • G11-1、G11-2 需要链接全部方块类与物品类（虚函数表要求每个虚函数都有定义），其中会引用 Level、Entity、网络等函数。做法：编译 world/level/tile、world/item、world/level/material、locale 下的 .cpp，其余被引用的外部函数由脚本从链接错误里收集符号、自动生成空定义（它们在 initTiles、initItems 期间不会被调用）。这是阶段 C 的第一项工作；若链接仍不可行，退而逐个读取参考源码里 initTiles、initItems 的构造与 setter 调用，在 harness 里只实例化基类来复现这些数据，并在手册里注明。
