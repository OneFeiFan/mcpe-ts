# 子代理审核方法与缓存成本

> 用途：全量审核时如何用子代理并行，以及怎样把缓存成本压到最低。最后更新：2026-10-24。

## 实测：中转支持提示词缓存

对 `api.tdcqcx.cn` 发 3 次**完全相同**的请求（system 带 `cache_control: ephemeral`，约 3300 token）：

| 请求   | input | cache_read |
| ------ | ----- | ---------- |
| 第 1 次 | 3333  | 0          |
| 第 2 次 | 134   | 3199       |
| 第 3 次 | 134   | 3199       |

结论：相同前缀从第二次起命中缓存，按缓存价计费。**“开子代理一定浪费缓存”不准确**，关键在分组方式。

## 子代理的缓存开销在哪

- 每个子代理是独立会话，读不到主会话的缓存；首次请求要写入自己的缓存。
- 并行的每个代理重复一份固定开销（CLAUDE.md、审核方案、PITFALLS 各读一遍）。
- 缓存 5 分钟过期；代理中途长时间空闲会重建。
- 一次性小任务只付写入、几乎不享受命中，最亏。

## 高效用法

1. **每组 3–5 个文件**，一个代理干几十轮，摊薄固定开销；不要一个文件开一个代理。
2. **同时最多 5 个**，实际先开 1 个试水，稳定后加到 2–3 个。老会话一次开 5 组，5 组全部 502。
3. **prompt 用同一模板**，只换文件清单与编号；不要把 C++ 原文贴进 prompt，让代理自己读。
4. **代理启动后连续干活**，5 分钟内持续请求，缓存一直热。
5. **机械活交给脚本**：`worksheet.py`、`clean.py`、`divs.py`、`ledger`、`rg`、`codegraph` 不花模型 token。
6. **主会话只留结论**：分组、验收、`pnpm check`、提交、更新待审清单；大段读文件/跑测试放子代理。
7. **子代理禁止** `git add/commit/stash`、禁止改 `待审清单.md` 与共享文件；主进程统一收尾。

## 标准 prompt 模板（要点）

- 仓库根目录、`$REF` 路径、当前分支。
- 必读：`CLAUDE.md`、`docs/全量审核方案.md`（8 步 + 35 条 + 禁止事项 + 第 9 节）、`docs/移植规范.md`、`.claude/skills/mcpe-porting/PITFALLS.md`。
- 名下文件清单（带行数）、对应 C++ 路径、本组连续 W 编号（如 W99–W103）。
- 本组重点：提前点出这类文件最容易错的地方。
- 严格流程：工作表逐行结论 → 读 `.h/.cpp` → 35 条逐项对照 → 每个修复先红后绿 → 验证 → 写审核记录 → 报告。
- 红态证据：`cp` 备份实现 → 临时改回旧行为 → 跑红记下断言原文 → `cp` 恢复 → 跑绿。不用 `git stash`。
- 验证命令（逐条看真实退出码）：`pnpm exec vitest run <测试文件>`、`npx tsc -p packages/world --noEmit`、`npx tsc -p tests/tsconfig.json --noEmit`、`npx prettier --check <改过的文件>`、`node tools/ledger.mjs`。
- **子代理里不要跑 `pnpm check`**（固定临时目录会与其他并行代理互相覆盖）。
- 报告格式：工作表行数、结论分布、改了哪些行（Wn）、红态断言原文与绿态测试数、ledger 前后条数、验证退出码、`DEFERRED(待确认)` 列表、有没有让已有测试变红。

## 文件所有权与编号

- 每组一段连续 W 编号；prompt 里写明“其他编号是别人的，绝对不要用”。
- 共享文件（`Tile.ts`、`TileInclude.ts`、`packages/world/src/index.ts`、`待审清单.md`、`全量审核方案.md`）只归主进程或明确指定的代理。
- 每组一个审核记录文件、一个测试文件，避免并行写同一个文件。

## 主进程收尾

1. 逐份核对子代理报告，抽查修改。
2. 主进程统一更新 `待审清单.md`。
3. 跑一次 `pnpm check`（类型 + 全部测试 + 台账，只打摘要）。
4. 按组提交，提交说明沿用 `全量审核（<批次>：<文件>）：Wn …；审核记录 <模块>.md`。
