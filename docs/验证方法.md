# 验证方法

每一步移植都要过三层验证，缺一不可：**类型检查与单元测试**、**黄金样本**（数值或字节格式有关的）、**浏览器实测**（画面上看得见的）。

## 1. 类型检查与测试

```bash
pnpm typecheck                       # 各包 + tests/ 的类型检查（vitest 本身不做类型检查）
npx vitest run tests/<路径>          # 只跑一个文件
pnpm check [测试文件…]               # 定型检查：typecheck + 测试 + 台账一次跑完，只打印摘要
```

全部测试一次跑完要五分钟以上，建议分三批跑：

```bash
npx vitest run tests/unit/world tests/unit/web --hookTimeout=200000
npx vitest run tests/unit/client tests/unit/util tests/unit/platform --hookTimeout=200000
npx vitest run tests/golden --hookTimeout=200000
```

截至 2026-10-09：122 个测试文件、1366 条测试，三批分别是 39 / 54 / 29 个文件。

**反向验证（变异测试）**：一次就过的测试要确认它真的会红。`node tools/verify/mutate.mjs <测试文件> <变异清单.json>` 逐条改坏实现、跑测试、再还原。变异清单是临时文件，用完不必提交。

## 2. 黄金样本

用参考 C++ 跑出来的标准答案。C++ harness 在 `tools/golden/harness_*.cpp`，产物在 `fixtures/golden/`（提交进仓库，开发机不需要编译器），TS 侧的比较在 `tests/golden/`。

### 怎么生成

```bash
REF=/path/to/minecraft-pe-reference bash tools/golden/build.sh            # 全部
REF=… bash tools/golden/build.sh features basictree                       # 只生成某几节；--list 列出全部节名
```

- 必须在 **x86-64 Linux 或 WSL** 上跑（越界 float→int 的语义、`MALLOC_PERTURB_` 都依赖它）。Windows 原生 MinGW 能算对数值，但 `registry.json` 依赖 `MALLOC_PERTURB_` 检测未初始化内存，**不要在 Windows 上重新生成**。
- `build.sh` 的通用编译参数里有 `-DOPENGL_ES`（网页版就是这么编的）；自己另写编译命令时别漏了这个宏，否则 `ModelPart::draw()` 会走显示列表分支。
- harness 只链接真正需要的 `.cpp`，缺的符号由脚本自动生成 `ud2` 陷阱桩：一旦运行到没提供的依赖就 SIGILL，等于把缺的依赖一条条指出来。
- 有未初始化内存的夹具要连跑两次（一次带 `MALLOC_PERTURB_`）再用 `merge-uninit.mjs` 合并，两次不同的字段标 `uninit`，不比较。
- 生成之后**立刻解析一遍**夹具，再看 `git diff fixtures/golden`。已有夹具重新生成后应逐字节不变。
- 用到 `Mth::sin` / `Mth::cos` 的 harness 必须先调 `Mth::initMth()`。

### 写新样本时要注意

- **样本要能分辨你关心的那个细节。** 大树的 6 棵树在 `abs` 用整数版或浮点版时都能通过，只有额外导出的 treeShape 表能分辨出来。不确定时故意改坏实现，看样本会不会红。
- 挑测试数据要验证它真的走到了想测的分支（地形的砾石阈值、窗口条件；世界生成样本的区块是否落在真实世界的 0–15 范围内）。
- C++ 侧的私有成员可以用 `#define private public` 读出来，但标准库头文件要在这之前 include。
- 需要固定随机序列时，可以用 `objcopy --weaken-symbol` 把 `Mth::random` 换成 harness 里的种子化实现。

## 3. 浏览器实测

```bash
node tools/verify/smoke.mjs tools/verify/scenarios/<场景>.mjs
```

场景脚本用 Playwright 打开开发服务器，通过 `window.__app`（`NinecraftApp` 实例）读写游戏状态、做数字断言、截图到 `tools/verify/out/`。

- **截图必须打开看**。脚本全绿不等于画面对：漏预加载贴图时，“画错了图”不会报任何错。
- `h.state` 的回调会被 `toString()` 后在页面里重新求值，**闭包全丢**，只能写字面量。
- 无头浏览器大约每秒 1 帧、每秒十几到二十刻。截一张图要好几秒，期间世界还在运行（睡觉 100 刻就会跳到天亮）；要拍某个瞬间，就得临时冻住那段逻辑。
- 世界 `pause` 之后才加入的实体，`xOld` 还停在 0，渲染插值会把它画到别处；先 `level.tickEntity(e, false)` 同步一次。
- 画面为空时，先用隔离实验区分是“测试设定的问题”（摆在近裁剪面里、在视锥外）还是“代码的问题”。
- 改过的选项会存进浏览器的 `options.txt`（IndexedDB），刷新也不会恢复。测试选项相关的界面时，要把“所有选项设到最大 / 最小后重启”作为固定检查项。

场景清单：`default`（进世界、放方块）、`startmenu`、`storage`（存档往返）、`worldgen`、`options`、`cursor`、`sign`、`falling`、`tnt`、`snowball`、`egg`、`arrow`、`particles`、`sound`、`entity-model`、`g10-renderers`、`g11-player`。

## 4. 台账

`pnpm ledger` 看 DEFERRED / OMIT / ADAPTED 的条数变化。把已有的 DEFERRED 换成真实调用时条数应该下降；新起一个类时没移植完的函数按 R3 留 DEFERRED，条数会上升——要紧的是每条新增都对得上具体哪句 C++。
